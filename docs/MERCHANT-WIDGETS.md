# Naara Widgets: operator and merchant guide (MASTER ONLY)

Permanently master-only (see CLAUDE.md). Spec of record: `docs/build-specs/26ba3cd1-NAARA-MERCHANT-WIDGETS-BLUEPRINT.md`.

## What it is
A merchant pastes one `<script>` (or installs the WordPress plugin) and their site sells Naara eSIMs, verification numbers and gift cards at the merchant price. Naara hosts the checkout, takes payment, delivers, supports the buyer, and accrues the merchant's margin (`widget:esim`, `widget:number`, `widget:giftcard`) into the normal merchant ledger.

## Turn it on (admin)
Admin > Widgets: switch on, review the limits (every one is a setting), save. Off by default; off means every widget route 404s.

## Merchant flow
Merchant > My Storefront > Widgets: create a key with the exact domains it may run on (no wildcards; add `www` separately), copy the snippet, or download the WordPress plugin pre-filled with the key. Rotate or revoke at any time; a revoke takes effect on the very next request.

## Security model in one paragraph
The key in the page is PUBLIC and only identifies. Every API call is checked live: key active, merchant active, request Origin/Referer host in the key's allowlist, product scope, per-key rate limit. CORS echoes only the matched origin. The hosted checkout page is the only page the app lets a third party frame, and only by that key's own domains (`frame-ancestors`, set per request). Money moves only through the existing gateway -> signed webhook -> `CreditWalletJob` rails; a failed fulfilment after payment refunds the buyer and records no earning. Held orders are never auto-delivered or auto-refunded.

## Files
- SDK: `public/widgets/merchant-widget.js` (vanilla, no eval, Shadow DOM; optional SRI via `MerchantWidgetSdk::integrity()`; pinning `integrity` needs your web server to send `Access-Control-Allow-Origin: *` for that one file).
- WordPress plugin source: `resources/merchant-widget/wordpress/naara-widgets/` (zipped on demand by `MerchantWidgetPluginPackager`; the download bakes in this install's address and the merchant's PUBLIC key, never a secret). Manual updates: wp-admin shows a notice when `/widget/plugin/version` reports a newer version.
- Tests: `tests/Feature/MerchantWidget*Test.php`; browser smoke: `node tests/visual/merchant-widget/widget-smoke.mjs`.

## Shopper experience (Clay skin, 2026-10-04)
The widget, the hosted checkout, the return page and the WordPress plugin settings all use the Naara **Clay** look (soft inflated cards, pressed inputs, pill buttons), light and dark. The hosted pages are self-contained on purpose (they live in a third party's iframe and cannot load the app bundle), so the skin is inlined there.
- **Widget:** "Pick one / Pay securely / Get it by email" strip, country search (matches country NAMES, not just codes) once a catalogue is large, "Show more" paging, value buttons for gift cards, loading skeleton, a "Confirming your payment" state, a receipt with a Buy-another link, and a full-screen modal on phones.
- **Hosted checkout:** step indicator, an order card with the plan's data/validity/countries, email with a typo catcher (gmial.com), only the gateway and currency pairs that actually work (no more "Paystack doesn't accept EUR"), an estimated local amount, a "what happens next" list and the order reference (NW-id). Light/dark follows the widget's `data-theme` (passed as `?theme=`), else the key's mode, else the shopper's device. The merchant accent arrives as `?color=`; text on it is chosen by contrast so a pale accent never gets white text.
- **Used or expired links** are still a 404, but the page now explains what happened and that nothing was charged.
- **Plugin v1.1.0:** set-up checklist (shows the exact site address to allow), a one-click connection test that runs in the admin's browser exactly as a visitor's page would, copy-ready shortcodes, block-editor connected/not-connected note, reserved space so the page does not jump.

## Verification numbers, My orders and browser features (2026-10-05, SDK v3, plugin 1.2.0)
- **Clear tabs.** The catalogue returns `kinds` (fixed order: eSIM data, verification numbers, gift cards) with a plain-language title, blurb and count. The widget shows them as tabs with a 3-step strip that changes per product, so a shopper always knows what they are buying. eSIM plans can be sorted (price, most data, longest validity) and searched by country name.
- **Verification numbers** (admin switch `Numbers on widgets`, OFF by default; the key needs the `number` scope). Flow: pick a service (admin-chosen list of up to ~20) -> pick a country (type-to-filter list, pre-selected from the browser's region) -> a LIVE price from `GET number-quote` (merchant lane, cached 45 s, cost and provider never returned; "not available right now" is said honestly) -> hosted checkout -> the receipt shows the number and the SMS code appears by itself when it arrives, with the refund countdown. If no code arrives within the refund window the order is refunded and the shopper sees "Refunded". The merchant's margin is booked only when the code arrives (`widget:number`, idempotent), never for a number that got no code.
- **My orders (shopper account)** (admin switch `Shopper account`, ON by default; merchant can also set `data-account="off"` / the plugin checkbox). Sign-in is an emailed 6-digit code (HMAC-hashed, 5 attempts, single use, 3 codes per 15 min per address, identical response whether or not the address has orders, so nobody can probe who shops there). The token travels only in the `X-Naara-Shopper` header, is stored hashed, scoped to one merchant, expires (admin days, default 30), and the 5 newest sessions per address are kept. A shopper sees only orders placed through THIS merchant: eSIM install link/QR/LPA/usage, number + live code, gift card details, refunded notes.
- **Control over their own data.** Download everything held (JSON), ask for deletion (one open request; lands in Admin > Widgets > "Shopper deletion requests" and alerts the admin; closing it is a manual, audited action), and sign out (revokes server-side).
- **Safe browser capabilities** (all on the shopper's own click, all optional, all degrade silently): copy to clipboard (with a fallback for blocked clipboards), Web Share, one-tap eSIM install on phones, "tell me when it arrives" notification (permission asked only on that click; the notification never contains the code), visibility-aware polling (slow in a background tab, pauses offline), localStorage for the token wrapped in try/catch, reduced-motion and dark mode respected. No cookies, no third-party calls, no fingerprinting, no geolocation. The SDK is pure ASCII on purpose (a host serving it without a charset cannot garble it; a test enforces this).
- **WordPress plugin 1.2.0:** `[naara_widget type="esim|number|giftcard"]` (empty = everything with tabs), new `[naara_account]` shortcode and a block option for a dedicated "My orders" page, a settings checkbox to switch customer sign-in off, connection test that reports numbers and sign-in. A "My orders" page linked from the merchant's menu is what brings customers back to the merchant's site.
- **Merchant dashboard:** the key form offers the `number` scope, the snippet generator offers a numbers-only snippet, margin earned for numbers is shown, and a "What your customers get" card explains the above (including `data-start="account"` for a plain-site My orders page).
- Tests: `MerchantWidgetNumbersTest`, `MerchantWidgetShopperAccountTest`, `MerchantWidgetDashboardTest`; browser: `node tests/visual/merchant-widget/widget-v3-smoke.mjs` (self-contained, mocks the API, 23 checks, light/dark, phone/desktop screenshots in `test-results/`).

## Honest limits
Numbers on widgets ship OFF: turn them on in Admin > Widgets only after one real sandbox purchase through your live number providers (tests fake the providers). Guest refunds return to the buyer's Naara wallet balance, not the original card. The shopper area is email-code only (no passwords, no social sign-in) by design. No WooCommerce integration and no private plugin update server yet. A real WordPress install, Safari/iOS framing and a screen-reader pass of the new screens are unverified. Shopper-facing legal copy (who is the seller of record, data-deletion promises) needs a lawyer's review before launch.

## Paid access and analytics (2027-01-24)

- **Paid or free, admin's call.** Admin > Widgets > "Charge merchants for Widgets" holds a switch and a one-time USD price. Off, or a price of 0, means free for everyone. On means a merchant pays once from their wallet (atomic debit, reference `mwa:{merchant}`, refunded and alerted if the record cannot be written, a double click never bills twice) before they can create or rotate keys, see the snippet or download the plugin. Purchases are kept for good: switching to free and back never takes access from someone who paid, and an admin can grant access without a charge. Live keys keep serving shoppers whatever the access state. Every price change is audited.
- **Analytics** (`MerchantWidgetAnalytics`): 7, 30 or 90 days with change against the previous period, a daily views, checkouts and orders chart, the four-step funnel, how orders ended, what sold, top sites, margin earned, and the latest orders with shoppers' emails partly hidden. Read-only; never returns a cost price.
